# Developer platforms and infrastructure

Use when visitors evaluate capability, integration cost, reliability, and scale.

## Page grammar

1. State the capability and boundary in plain technical language.
2. Show immediate use: runnable-looking code, request/response, terminal, or live output.
3. Map platform primitives into a coherent system.
4. Prove speed, accuracy, reliability, or scale with contextual metrics.
5. Show integration paths, templates, SDKs, and docs.
6. Address security, migration, operations, and pricing.
7. Close with a low-friction start and a sales path for complex deployments.

## Patterns from the corpus

- Supabase: a two-line promise, then the platform decomposed into useful primitives. Calm grid, white canvas, product-green syntax.
- Firecrawl: a sharper technical claim in a bordered instrument-like grid, followed by APIs, code, playgrounds, benchmarks, and use cases.
- Cloudflare: breadth organized around a single systems thesis and global network, using scale proof and pricing as product explanation.
- Stripe: complex financial infrastructure made legible through narrative groups, editorial diagrams, and a stable underlying grid.
- Content Architecture: technical credibility through visible repository structure and a single ASCII/terminal metaphor.

## Rules

- Code must be syntactically plausible and relevant to the adjacent claim.
- Separate primitives by the job they do, not by internal org chart.
- Prefer diagrams that show boundaries, flow, latency, or ownership; avoid abstract node clouds.
- Put docs near the first technical proof, not only in the footer.
- Benchmarks need a named task, comparison basis, and caveat; an orphan percentage is decoration.
- Open-source proof should show community, ownership, and deployment implications—not just a GitHub star count.
- Dense navigation is acceptable when labels map cleanly to user jobs. Use grouping and descriptions in mega menus.

## Example section

**Claim:** “Search, scrape, and structure any public page in one request.”

Pair it with a three-column proof: request → normalized document → downstream agent action. Follow with SDK tabs and a benchmark whose methodology is linked.

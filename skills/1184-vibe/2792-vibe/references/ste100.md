# STE-100 writing rules (for the Docs step)

Write every project doc in ASD-STE100 Simplified Technical English (STE).
STE makes text clear to all readers, including readers whose first language
is not English. This file gives the writing rules. It does not include the
STE controlled dictionary. If the project has a copy, use it for word choice.

`scripts/docs_gate.py` checks the rules marked **[gate]**. You must apply the
other rules yourself.

## Words

- Use one word for one meaning. Do not use synonyms for a thing you named before.
- Use simple, common words. Write "use", not "utilize". Write "start", not "initiate".
- Use technical names for things in the app (screen names, commands, fields).
  Write them exactly as the app shows them.
- Do not make noun clusters of more than three words. Write "the list of saved
  recipes", not "saved recipe list item view".
- Keep articles ("the", "a") and "this"/"these". Do not remove them to make a
  sentence shorter.

## Verbs

- Use these forms only: imperative, simple present, simple past, simple future,
  and the past participle as an adjective.
- Do not use "-ing" forms as verbs. Write "When you save the file", not "When
  saving the file".
- Use the active voice. Write "The app saves the file", not "The file is saved".
  In descriptions, the passive voice is permitted only when the doer is unknown
  or not important.
- Do not use phrasal verbs when a single verb is clear. Write "remove", not
  "take out".

## Sentences

- **[gate]** A procedural sentence (an instruction) has a maximum of 20 words.
- **[gate]** A descriptive sentence has a maximum of 25 words.
- Give one topic in each sentence.
- **[gate]** Do not use semicolons in prose. Make two sentences.
- Use a vertical list when a sentence has more than two items or conditions.

## Procedures

- Write one instruction in each sentence. Two actions in one sentence are
  permitted only when the user must do them at the same time.
- Use the imperative. Write "Run the command", not "You should run the command".
- Put the condition first. Write "If the test fails, read the log", not "Read
  the log if the test fails".
- Use numbered steps for tasks. Use bullets for items that have no sequence.
- A note gives information. A note does not give an instruction.

## Descriptions

- Put the most important information first in each paragraph.
- **[gate]** A paragraph has a maximum of six sentences.
- Give one topic in each paragraph.

## Warnings and cautions

- Start with a clear command. Then give the risk. Write "Do not delete the
  database file. You will lose all saved data."

## What each doc contains

| Doc | Reader | Contents |
|---|---|---|
| README.md | new user | What the app does (two sentences), install steps, quickstart, where to find more |
| PRD.md | developer | Problem, users, requirements (numbered, one testable behavior each), decisions, out of scope |
| FUNCSPEC.md | developer | Architecture, data, screens or commands, behavior of each feature, errors, limits |
| USERGUIDE.md | user | Tasks as numbered procedures, one section per task, troubleshooting |

Describe the current state only. Do not describe history. History goes in
CHANGELOG.md and the git log.
